# Professional skill anatomy
## Routing
The description identifies diff reviews and pull requests as target requests, even when the diff is provided directly in the notice. It is also triggered before merging, after implementing a feature, when reviewing code generated by humans or agents, during refactoring, and after bug fixes.

## Workflow
The workflow establishes quality gates before the verdict:
- Understand the context: identify purpose, specification, and expected behavior.
- Review the tests first: check coverage, boundary cases, and regression detection capabilities.
- Verify the tests through experimentation: mutation testing is recommended, temporarily modifying a condition and verifying that the tests fail.
- Review the implementation: analyze each file using the five quality axes.
- Categorize the findings: separate mandatory issues from optional suggestions.
- Verify the evidence: check tests, builds, manual testing, and visual evidence when applicable.
- Issue the verdict: Approve if it's ready for merge or Request changes if there are issues that need to be resolved.

## Review axes
|          Axes          |                                                                                                         Description                                                                                                        |
|:----------------------:|:--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------:|
| Correctness            | Verifies that the code does what the task or requirements specify. Checks boundary cases, errors, tests, incorrect conditions, race conditions, and inconsistent states.                                                   |
| readability/simplicity | Evaluates names, control flow, organization, unnecessary complexity, excessive abstractions, dead code, and logic that is difficult to understand.                                                                         |
| architecture           | Verifies that the change respects the existing architecture, the boundaries between modules, dependencies, and the appropriate level of abstraction. Also looks for duplication and complexity that has simply been moved. |
| security               | Looks for vulnerabilities such as unvalidated inputs, exposed secrets, authentication/authorization issues, SQL injection, XSS, vulnerable dependencies, and insecure use of external data.                                |
| performance            | Looks for problems such as N+1 queries, unbounded operations, excessive fetching, unnecessary synchronous operations, unnecessary renders, and lack of pagination.                                                         |

## Severity
The skill explicitly categorizes comments to distinguish between those that block the merge and those that are optional:
- No prefix: Required change; must be resolved before the merge.
- Critical: Blocks the merge due to serious issues such as vulnerabilities, data loss, or broken functionality.
- Nit: Minor, optional observation, such as formatting or style preferences.
- Optional/Consider: Suggestion worth considering, but not mandatory.
- FYI: Information requiring no action.

## Verification
Before closing the review, the Skill requires evidence that the change was actually verified:
- Successful tests.
- Successful build.
- Manual verification where applicable.
- Screenshots for UI changes where relevant.
- Before/after comparisons where necessary.
- For bug fixes, proper regression testing is required.
- Verification must document what changed and how it was verified.
- Critical issues must be resolved.
- Required changes must be resolved or explicitly deferred with justification.

## Composition
This skill is recommended to be combined with other specialized skills and references:
- security-and-hardening → detailed security review and supply chain risk assessment.
- performance-optimization → profiling and performance optimization.
- constraint-driven-development → broader analysis of mutation testing and mutation scoring.
- references/security-checklist.md → specific security checklist.
- references/performance-checklist.md → specific performance checklist.

## Boundaries 
The skill doesn't leave the final decision entirely to the agent. The recommended pattern ends with:
Model A → implementation → Model B → review → Model A → corrections → Human makes the final call

Additionally:
- It should not simply approve with a LGTM without evidence.
- It should not hide or downplay real problems.
- It should accept the author's override when they have sufficient context and a justifiable disagreement.
- It should not silently remove code if the agent is unsure whether it is unnecessary.
- It should not block based on personal preferences if the change improves the overall health of the code and follows project conventions.
- It should not silently perform destructive actions; for example, when identifying dead code, it should ask before removing it.
